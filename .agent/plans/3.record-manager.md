# Plan: Module 3 – Record Manager (content hashing + skip unchanged)

**Complexity:** ⚠️ **Medium** – one migration, small changes in 3 backend files and 2 frontend files, plus tests. The risk is the upload state machine (new / unchanged / updated / retry) and its failure paths, not the volume of code.


## Context
Today every upload creates a new `documents` row and re-embeds the whole file. Re-uploading the same file duplicates its chunks, so retrieval returns the same passage twice and embedding calls are wasted. PRD Module 3: *content hashing, detect changes, only process what's new/modified.* Learning goal: why naive ingestion duplicates, and how incremental updates work.

Nothing in `backend/app`, `supabase` or `frontend/src` hashes content yet. PROGRESS.md and context.md both list Module 3 as next, and context.md lists "No dedup yet" as a known limitation.

Out of scope:
- Model settings and roles page (PRD follow-up after Module 3).
- Metadata extraction (Module 4).
- Per-chunk hashing or partial re-embedding (considered and rejected: a changed file is fully re-chunked and re-embedded).
- Connectors or any automated ingestion.

## Decisions (confirmed with user)
- **Identity = (user, filename); version = SHA-256 of file bytes.** Same name + same hash → skipped. Same name + new hash → updated in place. New name → new document.
- **Identical re-upload:** no new row, no embedding calls. The UI shows "already ingested (unchanged)" and points at the existing document.
- **Whole-document reprocessing** on change: re-chunk and re-embed the file. No chunk-level hashes.

## Key design
**Hash source of truth is the server.**
- The client computes SHA-256 with Web Crypto *before* creating anything. This lets it skip the Storage upload for unchanged files.
- The backend recomputes the hash from the downloaded bytes in `run_ingestion` and stores *that* value. A client that lies only wastes its own work and never corrupts `content_hash`.
- If the client hash and the server hash disagree, mark the document `failed` ("content hash mismatch").

**`POST /documents` becomes the record-manager decision point.** Request: `{filename, size_bytes, content_hash}`. It looks up the row by `(user_id, filename)` under RLS:

| Existing row | Action | Response | Effect |
|---|---|---|---|
| none | `created` | 201 | insert `pending` row with hash |
| same hash, `completed` or `processing` | `unchanged` | 200 | no-op; return the existing doc |
| same hash, `failed` or `pending` | `retry` | 201 | reset to `pending`, keep id and storage_path |
| different hash | `updated` | 201 | set new hash and size, status `pending`, keep id and storage_path; old chunks are replaced at ingest |

Response shape: `{action, document}`.

**Concurrency:** a unique index on `(user_id, filename)` turns a double-click race into a 23505 error. Catch it, re-run the lookup and return the winning row's decision.

**Updated-in-place ingestion order.** Change `run_ingestion` to chunk and embed first, then delete the old chunks and insert the new ones. Today it deletes first. This shrinks the window where a document has no chunks. On embed failure the old chunks stay, and the doc is marked `failed` with its error. Keep the existing "delete chunks on failure" behaviour only for the first-ever ingestion, where no old chunks exist.

**Storage:** the update path overwrites the same `storage_path` (`{user_id}/{id}`) using upsert on upload.

## Phase 1 – Database
**Task 1.1 – migration `0003_documents_content_hash.sql`** (idempotent, like 0002):
- `alter table documents add column if not exists content_hash text;`
- Create `unique index if not exists documents_user_filename_key on documents (user_id, filename)`.
- Existing rows keep `content_hash` null. The next upload of the same name counts as "different hash" and is reprocessed once, which self-heals.
- **Pre-flight (manual):** `select user_id, filename, count(*) from documents group by 1,2 having count(*) > 1;`. If this returns rows, delete the stale duplicates via the UI before applying, because the unique index will otherwise fail.
- **Validate:** `supabase/tests/0003_record_manager_check.sql` inserts two rows with the same `(user_id, filename)` and expects a unique violation. It also checks that a second user cannot see the first user's rows.

## Phase 2 – Backend decision logic
**Task 2.1 – `services/record_manager.py`:** pure function `decide(existing: dict | None, incoming_hash: str) -> Literal["created","unchanged","retry","updated"]`, implementing the table above.
- **Validate:** `test_record_manager.py` has one case per table row plus a null stored hash → `updated`.

**Task 2.2 – schemas:** add `content_hash` (validated as 64 hex chars) to `DocumentCreate`, add the field to `DocumentOut`, and add `DocumentCreateOut`.
- **Validate:** a malformed hash returns 422 in `test_documents_router.py`.

**Task 2.3 – `POST /documents`:** look up the row by filename, call `decide`, apply the effect and return 200 or 201. Handle the 23505 race by retrying the lookup once. Keep the existing extension and size validation.
- **Validate** (router tests with FakeDB):
  - new file → 201 `created`
  - same hash completed → 200 `unchanged` with no insert or update
  - same hash failed → `retry`
  - changed hash → `updated`, same id, status `pending`
  - simulated 23505 → resolves to the existing row

## Phase 3 – Ingestion
**Task 3.1 – `run_ingestion`:**
1. Compute `sha256(bytes)` after download.
2. If the client-declared hash is known and differs, fail the document with "content hash mismatch".
3. Persist the server hash into `content_hash`.
4. Reorder to chunk → embed → delete old chunks → insert new chunks.
5. On failure, delete chunks only if the document had none before. Otherwise keep the old chunks and set `failed` with the error.
- **Validate** (`test_ingestion.py`):
  - hash stored on success
  - mismatch → `failed`
  - embed failure on an *update* leaves the old chunks intact
  - embed failure on a first ingestion leaves no chunks
  - re-ingest after update leaves zero stale chunks: `chunk_count` equals the new count and no old `chunk_index` rows survive

**Task 3.2 – storage upsert:** confirm `services/storage.py` and the client upload path support overwriting an existing object (`x-upsert: true` for httpx, `upsert: true` in supabase-js).
- **Validate:** extend `test_storage.py` with `httpx.MockTransport` and check the upsert header.

## Phase 4 – Frontend
**Task 4.1 – `lib/documents.ts`:** add `sha256Hex(file)` using `crypto.subtle.digest`. Update `uploadDocument`:
1. Hash the file.
2. Call `createDocument({filename, size_bytes, content_hash})`.
3. If the action is `unchanged`, return `{outcome: "unchanged", document}` and do NOT upload or ingest.
4. Otherwise upload to Storage with upsert, then call ingest.
5. On failure, delete the row only if the action was `created`. Never delete a pre-existing row on `updated` or `retry`; mark it failed via ingest/refresh instead.
- **Validate:** `npm run build` passes (type check); Playwright covers the behaviour (see end-to-end).

**Task 4.2 – feedback UI:** `DropZone` shows a notice per file: "Already ingested (unchanged)", "Updated – reprocessing…" or the normal progress.
- **Validate:** Playwright snapshot shows the notice text.

## End-to-end verification
1. `cd backend && venv/bin/python -m pytest` – all green. Baseline is 108 passed, and the new tests add to that.
2. `cd frontend && npm run build` – clean.
3. Apply `0003` in the Supabase SQL editor and run `supabase/tests/0003_record_manager_check.sql`.
4. `scripts/start-services.sh`, then Playwright MCP with a fresh `rlstest-*` user:
   - Upload `a.txt` → completes, N chunks.
   - Upload the identical `a.txt` again → "unchanged" notice, no new row, chunk count still N, and no new `ingest_document` trace in LangSmith.
   - Edit `a.txt` and upload → same row id, "updated", chunk count reflects the new text, and chat citations come only from the new content.
   - Upload `b.txt` with the same bytes as `a.txt` → new document, since identity is filename.
   - Upload two files at once with the same name → one row (unique index).
5. A second user uploading `a.txt` gets an independent row (RLS and per-user uniqueness).
6. Delete the `rlstest-*` users afterwards.

## Risks / ordering
- **Existing duplicate filenames** will block the unique index, so run the pre-flight query first.
- **`crypto.subtle` needs a secure context.** `localhost` works. A non-HTTPS deployment would need a fallback, which is out of scope here.
- **Fixed-size chunking:** any edit shifts later chunk boundaries, which is why whole-document reprocessing is the pragmatic choice.
- **`backend/.env.example` is uncommitted** and has had tunables removed. It is unrelated to this module, so leave it alone and keep the Module 3 diff separate.
- **Order:** Phase 1 → 2 → 3 → 4 → 5. Phases 2 and 3 can be built in parallel after the schema contract (`DocumentCreateOut`, `content_hash`) is frozen.

## Remaining open items
- Whether to backfill hashes for existing documents. Default: no, lazy self-heal on next upload.
- Whether the UI should offer a "re-ingest anyway" override for unchanged files. Default: no.
